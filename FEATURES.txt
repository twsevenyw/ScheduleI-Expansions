  ORIENTATION
  -----------
  This is ROADMAP EXPANSIONS: a shared framework library (EXPANSIONS CORE, in UserLibs) plus three
  feature mods (in Mods) that rebuild three announced-but-never-shipped Schedule I roadmap
  features -- Hireable Drivers, Police Improvements and Special Customers -- as native-feeling
  additions. Four DLLs, one of which is a library rather than a mod.

  All three feature mods are FULLY IMPLEMENTED. Read the status legend before you read anything
  else, because "implemented" here means something precise and limited: the source is complete,
  the solution builds at 0 errors and 0 warnings, every game and S1API symbol was verified
  against the real IL2CPP assemblies with a MetadataLoadContext harness, and all four DLLs are
  deployed. NO FEATURE MOD HAS EVER BEEN CONFIRMED WORKING END TO END IN A LIVE GAME. Section 12
  is the ordered list of things to check first.

  THE IN-GAME CONSOLE IS NO LONGER REQUIRED
  ----------------------------------------------------------------------------------------------
  Every verb in this suite is reachable from the Expansions screen. The console is still there and
  the commands below still work, but nothing depends on them. That matters because the console has
  two independent gates that are easy to trip:

    Per-save flag    ConsoleUI.IsConsoleEnabled comes from GameManager.Settings.ConsoleEnabled,
                     persisted in each save's Game.json. On a save where it is false there is no
                     keypress that opens the console.
    Binding / scene  The toggle is the BACKQUOTE key (`) through the new Input System, or hold
                     the left stick and click the right stick on a gamepad. ConsoleUI exists only
                     in the "Main" gameplay scene -- it never opens from the main menu.

  Both are handled from the Actions tab: "Enable and open the console" writes the per-save flag on
  the live settings object and opens the window; "Show the console key binding" reads the live
  binding back out of the game's input asset rather than quoting a constant, so a rebind in the
  game's own options is reported correctly.

 3.  EXPANSIONS CORE                                                  [SHIPPED]   v0.1.0
==================================================================================================

  The shared framework the three expansion mods hang off. Deployed as Expansions.Core.dll into
  UserLibs (not Mods) -- MelonLoader scans UserLibs first and registers it as a shared assembly
  resolution directory, so all three mods bind to one copy. It is a plain library, not a MelonMod:
  each expansion mod forwards its MelonLoader callbacks into Core, the first caller becomes the
  frame "driver", and the rest are ignored. One fan-out per frame whether you have one mod
  installed or three.

  Core holds ZERO compile-time references to Assembly-CSharp or FishNet. Every game type is
  reached by name through GameReflection. A renamed game type produces a logged warning, never a
  TypeLoadException that would stop Expansions.Core.dll loading and take all three mods with it.

  Core applies NO Harmony patches of its own.

  --------------------------------------------------------------------------------------------
  3.1  MODULE REGISTRY AND LIVE TOGGLES                                            [SHIPPED]
  --------------------------------------------------------------------------------------------
  - Every expansion registers as a module with a stable id, display name, version, description
    and config category. The menu lists them sorted by display name, so the order is stable
    regardless of MelonLoader's load order.
  - Each module gets an "enabled" setting, default on, persisted to Expansions.cfg. Modules never
    declare it themselves.
  - Toggling is live and reversible in BOTH directions -- from our menu, from a third-party
    mod-settings phone app, or by hand-editing the .cfg while the game is running.
  - Each module gets its own Harmony instance, "com.evan.expansions.<module_id>". Disabling
    unpatches only that module. Objects and subscriptions registered with the module's Lifetime
    are disposed in reverse order.
  - Registration is defensive: duplicate ids, categories containing a dot, categories colliding
    with the shared one, and already-claimed categories are all rejected with a warning rather
    than an exception. One bad mod cannot take down the others.
  - A module that throws 10 times in a frame hook during one enable cycle is switched off for the
    session. The PERSISTED toggle stays ON, so it retries next launch.
  - Core warns in the log if an expansion assembly is missing [assembly: HarmonyDontPatchAll],
    because MelonLoader would then auto-patch it under its own Harmony id and the reversible
    toggle guarantee would silently break.

  --------------------------------------------------------------------------------------------
  3.2  THE EXPANSIONS SCREEN                                                       [SHIPPED]
  --------------------------------------------------------------------------------------------
  One screen, two entry points: the "Expansions" main-menu nav entry, and F7 in-game.

  Layout:
      Heading "EXPANSIONS"
      Tab strip: [ Actions ] [ Tutorial ] [ Mods ]   -- opens on Actions
      Page area
      Output pane (Actions tab only)
      Footer: Diagnostics, Close, hint line

  - Built at runtime in uGUI/TMP by cloning live game GameObjects. No asset bundle, no shipped
    fonts, no shipped sprites -- this build has no loadable UI asset path, so cloning is the only
    option, and it also means the screen inherits the exact TMP font asset, SDF material, palette
    and hover behaviour the game uses.
  - Lives on its own DontDestroyOnLoad overlay canvas (sorting order 30000), which is why the same
    code serves the main menu and the in-game hotkey. Rebuilt on scene change; fonts, sprites and
    sounds re-harvested per scene.
  - Panel width switches with the tab: 640px for Actions and Tutorial (an action row carries a
    sentence and a button side by side, and a probe report path is 100 characters that must not
    truncate), and the measured 374px for the module cards, which are pixel-matched to the game's
    own and would stretch if widened. Three tabs at 104px plus two 6px gaps is 324, which still
    clears the narrow panel's inner width.
  - PANEL HEIGHT DERIVES FROM THE DISPLAY: 90% of Screen.height / canvas.scaleFactor, clamped
    between 360 and 1000 canvas pixels, and the page budget is the inverse of that. It used to be
    fixed constants, which on a tall screen wasted the space and on a short one hid the footer.
  - EVERY LIST SCROLLS -- actions, modules, tutorial chapters, the picker overlay and the output
    pane all run through one ScrollView: a ScrollRect host, a masked viewport carrying a
    TRANSPARENT RAYCAST CATCHER, top-anchored self-sizing content, and an auto-hiding scrollbar in
    a reserved 12px gutter. The wheel is applied by hand from Input.mouseScrollDelta with
    ScrollRect.scrollSensitivity pinned to 0, so there is exactly one implementation and it cannot
    double-apply. Dragging and the scrollbar handle stay on the component. PgUp / PgDn / Home /
    End / arrows work. The raycast catcher is the load-bearing part: Unity dispatches
    IScrollHandler by walking up from the raycast hit, and a Graphic-less viewport is not a
    raycast target, so before this fix the wheel silently did nothing anywhere on the screen.
  - Mods tab: one card per registered module with name, version, description and an
    Enabled/Disabled toggle, in a scrollable list. With nothing installed it says "No expansion
    mods are installed."
  - Tutorial tab: the whole-line controls in a toolbar (Start / Restart, Reset, Enable all,
    Disable all) over one row per chapter, each with its own on/off switch. See 4.7.
  - GAMEPLAY INPUT IS SUSPENDED while the screen is open, by reading the game's own
    StateProperties.UIDefault preset and calling StatePropertiesTransitionHandler.Transition,
    saving and restoring whatever was previously applied. That is the game's own mechanism for its
    own UI screens: it locks movement and camera look and frees the cursor. On a scene change the
    held state is DROPPED rather than restored, so the outgoing scene's properties cannot leak
    into the incoming one. The whole path is reflective, so a build where the type moved reports
    itself unavailable and falls back to a per-frame Cursor.lockState write.
  - Every game lookup degrades gracefully: a missing font falls back down a chain, a missing
    sprite falls back to a generated rounded rectangle, missing sounds go silent.
  - The main-menu injector waits 20 frames, then retries to frame 180. If it never injects, the
    whole menu falls back to the IMGUI surface. If it injected once and fails on a later scene, it
    keeps the native screen and logs that F7 still works.

  --------------------------------------------------------------------------------------------
  3.3  THE OUTPUT PANE                                                             [SHIPPED]
  --------------------------------------------------------------------------------------------
  Below the action list. Timestamped, colour-coded by outcome, wrapping, auto-scrolled, holding
  the last 60 lines. Every action result, probe summary, file path and error lands here AND
  mirrors to the MelonLoader log. Modules push into it with ActionLog.Ok / Note / Fail.

  This exists because the owner cannot rely on the in-game console: an answer that only reaches
  the MelonLoader window behind the game has, for practical purposes, not been delivered.

  BOUNDED AND COLLAPSIBLE. The pane is capped at 32% of the page and has a Hide / Show control in
  its header strip, persisted as output_pane_open. Collapsed, it is just the 26px header and the
  list gets the rest of the page; it keeps recording either way. This was a fixed 168px slice the
  action list could never reclaim, which with a 372px list cap and about 3,100px of action content
  left roughly five of the then 46 actions reachable. On a 1080p display it is now about nine
  action rows expanded and eleven collapsed.

  --------------------------------------------------------------------------------------------
  3.5  ACTION REGISTRY (the API modules use)                                       [SHIPPED]
  --------------------------------------------------------------------------------------------
  Process-wide, the third registry a module contributes to alongside ProbeRegistry and
  TutorialRegistry:

      Lifetime.Add(ActionRegistry.Register(new ExpansionAction(
          id:          "special_customers.tp_visitor",
          label:       "Teleport to Marcus Vale",
          description: "Puts you a step in front of the Northtown motel visitor.",
          isAvailable: () => VisitorRuntime.StatusOf(slot).WrapperResolved,
          invoke:      () => Teleport())));

  - ActionAvailability converts implicitly from bool and from string; a string is ALWAYS a
    refusal, and becomes the greyed-out reason shown beside the button.
  - ActionResult converts implicitly from string and bool.
  - Three constructor shapes: plain (Func<ActionResult>), void (Action), and picker
    (choices: + invokeChoice:), the last of which opens a searchable list.
  - ExpansionAction.WithDynamicLabel for a button whose verb changes with state.
  - Group is derived from the id prefix before the first dot, resolved through the module
    registry, so "police_overhaul.x" heads its section as "Police Improvements". group: and
    order: override.
  - Register returns IDisposable; RegisterAll(...) returns one token for the lot.
  - Duplicate ids are rejected with a warning and an inert token.
  - Availability predicates are re-read EVERY FRAME the screen is open, so anything expensive
    sits behind a short-TTL cache: the ConsoleUI heap walk 1s, the NPC registry 2s, session state
    0.5s, the report directory 2s.

  --------------------------------------------------------------------------------------------
  3.6  DIAGNOSTICS HARNESS                                                         [SHIPPED]
  --------------------------------------------------------------------------------------------
  Read-only runtime interrogation. Full probe list in section 9.

  Running it:      Actions tab ("Run all diagnostics probes" / "Run one area of probes"), the
                   footer Diagnostics button, P while the screen is open, or "expprobe".
  Output:          <GameDir>\UserData\Expansions-Probe-<timestamp>.md, plus a sidecar
                   -avatars.json when the avatar dump runs. The path is written into the output
                   pane, and "Open the newest probe report" reveals it in Explorer.
  Grep handle:     every probe emits a line "RESULT:<probe_id>:<status>".
  Report tail:     a "Requires a mutating test" section listing the questions no read-only probe
                   can answer -- 20 from Core plus 4 registered by Hireable Drivers -- each with a
                   step-by-step recipe.
  Safety:          each probe is isolated; one throwing is recorded FAILED and the run continues.
                   The report is written even if every probe fails. Probes needing a loaded save
                   report INCONCLUSIVE on the main menu. Every lookup is late-bound.
  Opt-in probes:   a probe that can end the PROCESS rather than merely fail is marked explicit-
                   only. It is skipped by bare "expprobe", by the Diagnostics button, by the
                   Actions-tab runners and by any area or prefix selector, and additionally needs
                   allow_mutating_probes = true and a loaded save.
  Crash journal:   every native step of an opt-in probe writes BEGIN/END through an unbuffered
                   write-through FileStream and flushes to disk before acting. A BEGIN with no END
                   is promoted to Expansions-Probe-quarantine.txt on the next run, reported, and
                   skipped from then on. Converges a bisect in about two runs instead of 31.

  --------------------------------------------------------------------------------------------
  3.7  TUTORIAL DIRECTOR                                                           [SHIPPED]
  --------------------------------------------------------------------------------------------
  Runs the quest line as real S1API quests, 50 XP per chapter via LevelManager.AddXPLocal.
  Progress persists per save. Core ships every chapter as a placeholder and each feature mod
  replaces its own with real objectives on enable -- and puts the placeholder back on disable, so
  toggling a mod off degrades its chapter to "coming soon" rather than leaving a hole. Six
  chapters register in this package. Full content in section 8.

  IT HAS ITS OWN TAB. With 47 actions, three module cards and six chapters, one scrolling column
  would bury all three, so the Tutorial tab carries:

      Toolbar        Start / Restart (dynamic label), Reset, Enable all, Disable all
      One row        per chapter: title, description, current state, and an on/off switch
                     per chapter

  Start / Restart and Reset are still registered as Core actions too, so nothing that used to work
  by action id stopped working. From the main menu the line arms itself and begins on load.

  PER-CHAPTER ON/OFF. A switched-off chapter shows "Skipped", the director steps over it, and it
  contributes no journal objectives. It is deliberately NOT marked complete, so switching it back
  on replays it rather than skipping it forever.

  The switches persist as ONE comma-separated list, tutorial_disabled_chapters, under the shared
  [Expansions] category -- not one entry per chapter. Chapters arrive at runtime from whichever
  mods happen to be loaded, so an id belonging to a mod that is not installed has to survive the
  round trip rather than be dropped on write.

  Core's chapters were verified end-to-end in a live game (2026-08-03) -- four of them on the
  owner's machine, three of which are the three that register here. The three feature chapters
  have not been verified.

==================================================================================================
 4.  THE ACTIONS SURFACE -- every action, by owning mod
==================================================================================================

  47 actions are declared across the four projects, and all 47 are expected to reach the screen.

      Expansions Core .......... 16
      Hireable Drivers ......... 13
      Special Customers ........ 10
      Police Improvements ....... 8

  The Police group used to declare 8 and register 0. It bound Core's action API by reflection
  against a five-argument constructor that does not exist, so every registration threw
  MissingMethodException and the log read "Registered 0/8 police menu action(s) with Core." It now
  calls ActionRegistry.Register with the typed API -- every mod has a ProjectReference to Core, so
  the call is compile-checked -- and the ids were re-prefixed from police.* to police_overhaul.*
  so the group derives the heading "Police Improvements" from the module id. Fixed in source,
  builds clean, NOT yet seen on a screen.

  Groups are sorted with Core first, then feature modules alphabetically by display name. Within a
  group, by the action's own order value, then label.

  A row marked "picker" opens a searchable overlay list instead of running immediately. The search
  box reads Input.inputString; the screen now holds the game in its UI state, so typing no longer
  moves the player.

  v0.4.0 REWORKED THE ENTIRE SURFACE. In v0.3.0 you hired a driver from a menu action and edited
  routes in a custom IMGUI panel on F6. Both are gone. You now hire a driver from the
  employee-fixer NPC's own conversation, and you edit routes on the game's own management
  clipboard -- the same clipboard, the same five rows, the same worldspace endpoint picker every
  other employee uses. F6 is now a read-only diagnostic view. If you are reading an older revision
  of this document, the F6 panel and the route-editing actions it describes no longer exist.

  WHAT IT IS
  --------------------------------------------------------------------------------------------
  You already have Handlers who shuffle items around inside one property. A Driver does the same
  job BETWEEN properties, businesses and dealers, using one of your cars. Same hiring, same wages,
  same bed requirement, same five-route grammar. The only new verbs are "assign a vehicle" and
  "depart when the trunk holds N items" -- which is the dev's own wording from Community Vote #2.

  A driver is a real vanilla Packager (EEmployeeType.Handler) whose packaging brain is suppressed
  during a trip and whose movement a managed state machine owns. It is NOT a new Employee
  subclass: FishNet's weaver runs at build time only, so an injected subclass would get no RPCs,
  no SyncVars and no spawnable prefabId, and Employee.Initialize would never replicate its name,
  appearance or assignment.

  HIRING -- ON THE FIXER'S OWN DIALOGUE, WITH ZERO HARMONY PATCHES
  --------------------------------------------------------------------------------------------
  The employee-hiring NPC's DialogueController_Fixer gets ONE EXTRA INTERACTION CHOICE PER
  PROPERTY, added through the game's public DialogueController.AddDialogueChoice -- the same
  extension point the shipped controllers use for "Give them product".

      Hire a driver for the Barn ($1,800)
      Hire a driver for the Docks Warehouse ($1,800, 2 slots)

  The game draws them in its own list with its own font, sounds and gamepad handling, re-runs each
  entry's visibility check every time you open the conversation, and fires the choice through its
  own click path. Selection works because it is the game's selection. Consequences:

     - A property with no free driver slot IS NOT OFFERED. The fee and the free-slot count are
       recomputed by the visibility check every time the conversation opens, so the label is never
       stale.
     - Nothing is grafted onto the dialogue GRAPH. Node links live in ScriptableObject data the
       mod cannot author, so a choice that routed into a new conversation branch would dead-end.
       These are action-only choices: Conversation is left null and the choice simply runs its
       onChoosen event.
     - The attach is retried from the tick pump for 40 attempts, because the Fixer is a scene
       object that is not guaranteed to be awake when the scene-loaded event fires. If it never
       takes, the log says so and the Expansions menu's "Hire a driver (fallback)" action ungreys
       itself. That action is greyed out with a pointer to the fixer whenever the hook DID take,
       deliberately: an always-available menu shortcut would quietly become the path everyone
       uses and the native surface would rot.

  DRIVER SLOTS ARE A SEPARATE BUDGET FROM EMPLOYEE CAPACITY
  --------------------------------------------------------------------------------------------
  One driver per property regardless of how many botanists, handlers, chemists and cleaners are
  already there; two at the docks warehouse, because that is the freight property.

     driver_slots_per_property = "*=1,dockswarehouse=2"
     drivers_use_employee_capacity = false      (default -- flip it to spend real employee slots)

  Keys are real Property.propertyCode values, read out of shipped save data rather than guessed
  from display names: barn, bungalow, dockswarehouse, manor, motelroom, rv, seweroffice,
  storageunit, sweatshop, and the businesses carwash, laundromat, postoffice, tacoticklers. "*"
  is the fallback for anything unlisted, and a value is clamped 0-16.

  UPKEEP
  --------------------------------------------------------------------------------------------
     Signing fee        $1,500 base, plus $100 for every employee you already own, counted across
                        ALL your properties -- the same escalation the shipped employees use.
                        Between the shipped Handler ($1,000) and Chemist ($2,000).
     Daily wage         $250/day, drawn from the bed's locker by the vanilla wage pipeline. There
                        is no separate driver economy.
     Bed                Required by default. Without one the driver refuses to work and says so
                        on the clipboard. require_bed_and_wage = false lifts it.
     Working hours      07:00 to 04:00, the shipped day window.
     Curfew             Ignored by default, matching the shipped rule that dealers cannot be
                        arrested. respect_curfew = true makes them stop.
     Vehicle            A new driver auto-claims the first unclaimed vehicle you own, so a route
                        works straight away. A driver whose van was sold picks up another as soon
                        as one is free. A vehicle is claimed for the duration of a trip, so two

  ROUTES -- EDITED ON THE SHIPPED CLIPBOARD
  --------------------------------------------------------------------------------------------
  A driver is a Packager, so the shipped PackagerConfigPanel already binds five RouteEntryUI rows
  to PackagerConfiguration.Routes. The mod lets that field own the routes, which buys the real
  in-world source/destination picker, the transit-line preview, the item-filter screen, FishNet
  replication and vanilla save/load for free, rather than a mod list that only looks like one.

  Point the clipboard at a driver and you get Bed, Stations and Routes. Stations is refused with
  a reason ("Drivers run transit routes, not stations.") because a station assigned to a driver
  would silently never be worked. The five Route rows are the editor:

     From          Storage at THE PROPERTY THE DRIVER WAS HIRED TO. Shelves, racks, packaging
                   stations, presses, pots, mushroom beds, drying racks, ovens, cauldrons, mixing
                   and chemistry stations, loading docks.
     To            Any of the above ANYWHERE YOU OWN, or a recruited dealer.
     What          The vanilla item filter, or blank for "anything the source holds".
     Depart at     Item count. Not a vanilla field, so it lives on the Expansions menu.
                   0 means automatic: default_depart_threshold_percent of the trunk's capacity.
     On / off      Per row.

  PICKUP IS PINNED TO THE HIRING PROPERTY, ENFORCED IN THREE PLACES: inside the game's own
  worldspace picker (a postfix on RouteEntryUI.ObjectValid, so hovering an invalid container shows
  "Driver X only collects from the Barn" and clicking it does nothing), on every pull from the
  clipboard, and on load, where a violating route from an older save or a co-op peer is rejected
  and logged. That is the whole point of hiring at a property.

  DESTINATIONS ARE WIDENED, not narrowed: the same postfix OVERTURNS vanilla refusals for any
  entity that accepts items, because a Handler may only route within its own property and a driver
  crossing town is the entire feature. It only overturns refusals about REACH -- a destination
  that is already this route's own pickup is still nonsense and keeps the vanilla message.

  The clipboard's picker is range-limited, so a warehouse on the other side of town cannot be
  clicked and a dealer is not an ITransitEntity at all. Those two cases are why the Expansions
  menu keeps a drop-off picker.

  MIRRORING. The transport loop reads DriverRecord.Routes, so the vanilla field is mirrored into
  it once per tick by POLLING, not by subscribing to RouteListField.onListChanged -- that event is
  a UnityEvent<T> over a game generic, and a collected interop delegate fails silently, which is
  the one failure mode this module refuses to ship. A record written before v0.4.0 pushes its
  routes onto the clipboard once (RoutesOnClipboard), and after that the clipboard is the record
  of truth: deleting a row there deletes it.

  A row also times out: depart_after_game_hours (default 4) sends a partly-loaded van rather than
  letting a slow source deadlock the route. 0 waits forever.

  A route is skipped, not failed, when the source has nothing matching, the destination is not
  accepting items, or a dealer destination is already stocked to the cap.

  THE TRANSPORT DECISION -- the load-bearing part                                  [UNVERIFIED]
  --------------------------------------------------------------------------------------------
  The whole feature turned on one fact nobody could settle from metadata: whether civilian vehicle
  prefabs actually carry a VehicleAgent. It is inspector-wired, only police consumers appear in
  the dumps, and it cannot be added at runtime. Rather than bet on it, the mod decides PER TRIP,
  PER VEHICLE and carries both paths:

     DRIVE   The game's own autonomous stack. Navigate on the A* road graph, DriveFlags for
             per-trip style, a reverse-then-teleport stuck ladder, Park at the far end.
     RELAY   The van and driver relay to the far end after a travel-time delay derived from
             straight-line distance -- the same abstraction the game already uses for its own
             supplier deliveries.

  VehicleApi.CanSelfDrive requires a VehicleAgent AND both Seekers AND a VehicleTeleporter. A
  non-null Agent alone is not trusted, because a half-wired one would fail mid-road.

     transport_mode = auto     drive when the vehicle qualifies, otherwise relay  (default)
     transport_mode = drive    driving only; a trip refuses if the vehicle cannot
     transport_mode = relay    always relay, skipping the per-trip check

  BOTH PATHS DELIVER. Only the cross-town leg differs. Collection, deposit, slot locking, capacity
  checks, wages, persistence and the time-skip snap are shared code.

  THE TRIP STATE MACHINE
  --------------------------------------------------------------------------------------------
     Idle -> ToSource -> AtSource -> Loading -> ToDestination -> AtDestination -> Unloading
          -> GoingHome -> Idle,  with Recovering as the failure exit

  Notes on the ones that are not obvious:

     AtSource /       Walks to the entity's reachable access point. After 20 in-game minutes of
     AtDestination    not arriving it warps the last stretch, because storage behind a door the
                      NavMesh will not path through is otherwise a permanently dead route.
     Loading          Moves a batch every LoadMinutesPerStop/6 in-game minutes. Departs when the
                      threshold is met, the source runs dry, patience runs out, or three
                      consecutive transfers move nothing.
     Unloading        Anything that will not fit at the far end STAYS IN THE TRUNK, which is a
                      real container you can open. Nothing is destroyed or dropped. The driver
                      files a clipboard issue naming what is stuck.
     Recovering       Files a clipboard issue with a reason and a fix, releases the vehicle claim
                      and any slot locks, hands movement back to vanilla, and cools down 60
                      in-game minutes.

  Every refusal writes a one-line status the panel and the roster action show verbatim: "No
  vehicle assigned.", "Needs a bed and a day's wage in it.", "Off shift. Drivers work 07:00 to
  04:00.", "Nothing to move -- the source is empty or the destination is full."

  DEALERS AS DESTINATIONS
  --------------------------------------------------------------------------------------------
  A recruited dealer can be a route destination. Delivery is a single atomic tick through
  AddItemToInventory, capped at dealer_topup_cap (10, matching the dealer's ten inventory slots).
  The dealer's home building is the parking anchor. No slot reservation is taken, because a dealer
  inventory is not a TransitEntity.

  SLEEP AND TIME SKIPS
  --------------------------------------------------------------------------------------------
  A trip in flight when the clock jumps is collapsed to its end state in one pass -- collect to
  threshold, snap the outbound leg, deposit, snap the homeward leg -- exactly as the game's own
  NPCSignal_DriveToCarPark.JumpTo does. You wake up to "Delivery completed while you slept", not
  a van abandoned mid-junction. If anything in that resolution throws, the driver is parked at
  home instead and the trip is reset.

  THE F6 PANEL -- READ-ONLY DIAGNOSTICS
  --------------------------------------------------------------------------------------------
  This used to be the route editor. It is not any more. What a clipboard cannot show is WHY a
  driver is standing still, so that is all this is:

     - Per-property driver slot usage.
     - Each driver's state and, if it is not working, the reason in its own words.
     - The route rows exactly as the transport loop currently reads them, flagging any endpoint
       that no longer resolves.
     - Binding failures.

  Still IMGUI and still absolute-rect GUI.Box / GUI.Label / GUI.Button, because this build strips
  TextField and breaks DrawTexture, and a diagnostic view has no business owning a canvas. 720 x
  520, Escape or F6 closes it.

  THE CORE IDEA
  --------------------------------------------------------------------------------------------
  The game has no heat system, no persistent law reputation and no jail. What it DOES have is a
  complete, designer-authored, minute-ticked law scheduler covering patrols, checkpoints,
  sentries, vehicle patrols and curfew -- every entry of which gates itself on one integer,
  LawController.LE_Intensity.

  So this mod does not build a parallel police spawner. It keeps a persistent per-player HEAT
  scalar, maps it onto that integer and the schedule data behind it, and lets the game's own
  scheduler put the officers out. Every write is RAISE-ONLY against the designer's own numbers, so
  AT HEAT 0 THE WORLD IS EXACTLY VANILLA. internalLawIntensity is never written, so Law.json stays
  byte-identical and disabling the module leaves the save unchanged.

  --------------------------------------------------------------------------------------------
  PILLAR 1 -- HEAT                                                    enable_dynamic_intensity
  --------------------------------------------------------------------------------------------
  A 0-100 float per player, persisted to <save>\Modded\Saveables\expansions_police.json. It
  deliberately survives sleeping -- otherwise it would be a rename of the shipped wanted level,
  which sleeping wipes.

  WHAT RAISES IT
     Committing a crime      the game's own fine for that crime x 0.2, times quantity. The fine
                             values are read from PenaltyHandler AT RUNTIME, so the mod inherits
                             the game's own severity ranking and re-calibrates itself to future
                             balance patches instead of carrying its own opinion.
     Getting arrested        +15
     Completing a deal       +1 per $2,000 of contract payment, capped at +15 per in-game day
     During curfew           crime heat x1.5
     By district             Uptown / Suburbia x1.25 -- Downtown / Westville x1.0 --
                             Northtown / Docks x0.85

  With the shipped fine table that works out as: $5 possession -> +1, $50 evading -> +10, $100
  curfew violation -> +20, $150 attempting to sell -> +30.

  WHAT LOWERS IT
     Sleeping           heat_decay_per_day (10) per slept day, NET of whatever already drained
                        live, so a clean day always totals exactly the daily figure
     Lying low          heat_decay_per_clean_minute (0.004) per clean in-game minute, delivered
                        live so the read-out visibly rewards keeping your head down

  THE FIVE TIERS
     Tier              Heat     Officers/post   Checkpoint window   Detection   Search x   Fine x
     ---------------   ------   -------------   -----------------   ---------   --------   ------
     T0  Calm           0-19    1 / 1           shipped               1.00        1.00      1.00
     T1  Alert         20-39    1 / 2           shipped               1.10        1.25      1.25
     T2  Crackdown     40-59    2 / 3           +/- 2 h               1.25        1.50      1.50
     T3  Task Force    60-79    2 / 4           +/- 6 h               1.50        2.00      1.75
     T4  Federal      80-100    3 / 4           +/- 12 h              1.75        2.50      2.00
                                                                     (memory 2.0 at T4)

  The officer bands are a FLOOR, never a ceiling: callers take the larger of the band and the
  designer's own number for that post. A mod called "police improvements" must never quietly staff
  a checkpoint more thinly than the base game did. T1 is exactly vanilla -- v0.4.6 shipped "1-2
  officers instead of 2 all the time". 4 is the game's own hard dispatch cap and is never
  exceeded.

  Heat adds heat/12.5 x intensity_scalar (capped at +8) to the vanilla intensity baseline, clamped
  into the game's own 1-10 range.

  --------------------------------------------------------------------------------------------
  PILLAR 2 -- WHICH LEVERS ACTUALLY GET PULLED
  --------------------------------------------------------------------------------------------
  This is where the design met reality. Of the 31 police tuning statics the plan wanted to
  modulate, 28 turned out to be C# consts that IL2CPP inlined -- writing one is not just useless,
  it can kill the process (see section 13). Only three are real writable statics:
  VisionCone.UniversalAttentivenessScale, VisionCone.UniversalMemoryScale, and
  LawManager.DISPATCH_VEHICLE_USE_THRESHOLD.

  So the module drives the world through instance-level and patch-level twins instead:

     Officers per post    the schedule data's own MinMembers / MaxMembers, plus a raise-only
                          clamp on PoliceStation.Dispatch          (enable_schedule_tuning)
     Checkpoint hours     widening the shipped windows on the same schedule data
     Detection            per-officer VisionCone.RangeMultiplier and BodySearchChance -- these
                          are INSTANCE fields and cannot be const-inlined
     Everything else      18 Harmony patch targets on the decision methods themselves

  The module is built so the writable-static count can be ZERO and every pillar still works. The
  police.levers probe reports which statics were writable on your build and which fallbacks are
  carrying the load. Both the schedule numbers and the per-officer values are snapshotted on
  enable and written back on disable, and the restore ends in CurrentSettings.Evaluate() so the
  game re-derives the whole world once from fully vanilla data.

  --------------------------------------------------------------------------------------------
  PILLAR 3 -- CONSEQUENCES                                                   enable_consequences
  --------------------------------------------------------------------------------------------
  The shipped arrest is nearly free: $5-$150 per charge, cash only, no debt if you cannot pay, and
  vehicle cargo untouched entirely. This closes that.

     Fine multiplier        the tier multiplier above, times outlaw_fine_multiplier (2.0) while
                            outlawed
     Notice honesty         the surcharge is added to the arrest notice's own penalty list, so
                            the number you read is the number you pay
     Confiscation scope     the stealth argument on RecordPossession and ConfiscateItems is
                            widened, so Advanced packaging stops being a get-out-of-jail card
     Vehicle cargo          contraband in the vehicle you were arrested next to is seized, with a
                            notification naming how many stacks   (confiscate_vehicle_cargo)
     Cash, THEN DEBT        the fine takes your cash; anything you cannot cover is taken out of
                            your ONLINE balance                    (enable_debt)

  THE DEBT LEVER IS THE REAL DIFFICULTY KNOB. Everything else is texture. The shipped economy
  makes cash abundant and online balance scarce -- $10,000/week of ATM deposits, $20,000/24h of
  laundering. A $300 cash fine against a $50,000 pile is nothing; $300 off the online balance is
  the only currency you cannot simply go and earn faster.

  Self-calibrating charge: the module measures your cash across the arrest notice opening and
  closing, and charges only the shortfall. If vanilla already charged, it tops up; if vanilla
  charged nothing, it charges in full. It logs which it learned, and the police.world_state probe
  reports it as "Base game charges its own fine: yes / no / unknown until the first arrest". This
  retired an open risk without needing a probe.

  --------------------------------------------------------------------------------------------
  PILLAR 4 -- OUTLAW STATUS                                                        enable_outlaw
  --------------------------------------------------------------------------------------------
  Heat is the pressure; Outlaw is the phase change. A latched three-state ladder that changes
  RULES rather than the world.

     CLEAN  -> MARKED     heat reaches outlaw_heat_threshold (90)
     MARKED -> HUNTED     a second federal encounter, or a second arrest while outlawed
     Down one tier        outlaw_clear_days (3) consecutive in-game days with no crimes and no
                          arrests, or the "clear outlaw status" action

  Dropping a tier also pulls heat back below the latch threshold so you do not instantly re-latch.

  While outlawed: every officer is permanently flagged as knowing you on sight (a visibility label
  the module applies and removes by name), body searches always find something, vehicle searches
  always find something, pursuits do not evaporate on a brief loss of line of sight, and fines are
  doubled. All of it is snapshot-and-restore from a single Revert() call.

  --------------------------------------------------------------------------------------------
  PILLAR 5 -- FEDERAL AGENTS                                              enable_federal_agents
  --------------------------------------------------------------------------------------------
  Mechanically the game's own PoliceOfficer type, spawned and owned by the mod. What makes them
  different is the per-officer tuning: always search, much better eyes and memory, and they do not
  give up.

  RUNTIME VIABILITY CHECK, RUN BEFORE ANYTHING IS SPAWNED
     1. Is "PoliceNPC" a registered FishNet spawnable? If yes, instantiate from the network
        prefab.
     2. Otherwise, is there a live officer to clone? If yes, clone it and re-run the FishNet
        initialisation trio.
     3. If neither, Spawn returns 0, the reason is logged and reported by the probe, and NO OTHER
        PILLAR IS AFFECTED. Heat, intensity, consequences and outlaw do not depend on this.

  Whether either path works on this build is genuinely unknown. The police.federal_agents probe
  answers it read-only, but note that the clone path needs at least one live officer to exist, so
  running it from the main menu will report "no" for the wrong reason.

  SAFETY: agents are never added to PoliceStation.OfficerPool (so the vanilla dispatcher cannot
  send a federal agent to a jaywalking call), ShouldSave is forced false for them, and they are
  removed from both registries on despawn. They cannot reach your save.

  LOOK: built by SUBTRACTION from a real officer. Drop the police cap and the marked bulletproof
  vest, keep a plain navy vest, swap the duty belt for an ordinary belt, add a charcoal blazer,
  Oakleys and dress shoes. Local PD reads black plus duty-belt clutter; federal reads
  navy/charcoal. Charcoal blazers are reserved for federal agents across the whole suite -- the
  Special Customers businessmen deliberately use navy and brown.

  WHEN THEY TURN UP: heat at or above federal_heat_threshold (80) held for a full in-game day,
  checked hourly, two agents per event, six in-game hours, two in-game days of cooldown. Or
  immediately from the menu action.

  THE POOL
  --------------------------------------------------------------------------------------------
  Eight reusable NPC bodies (expansions_sc_visitor_01 .. _08), re-dressed per archetype rather
  than one NPC type per archetype. Eight is about a 10% increase over the game's ~80 NPCs; thirty
  would be 37%, and every one of them streams to every client on join. It is also exactly how the
  game builds its own cartel goons.

  Marcus Vale is the group's ADVANCE SCOUT and the only pool member visible between visits -- he
  stands on the Northtown motel forecourt, and he is the leader when a group is in town. Slots
  02-08 sit hidden, parked and zeroed so they generate nothing.

  A Customer component is attached at PREFAB time, not after spawn. That deliberately sidesteps
  the module's single biggest unknown -- whether a Customer added after the NetworkObject spawns
  replicates at all -- by putting it on before S1API network-spawns the prefab.

  THE VISIT LOOP
  --------------------------------------------------------------------------------------------
     Cadence        Every visit_interval_days_min..max (2-3) in-game days. One group at a time,
                    ever. Weighted archetype pick, never the same group twice running while an
                    alternative exists.
     07:00          Region chosen by the archetype's own weights, restricted to unlocked regions
                    (falling back to whatever IS unlocked rather than silently never visiting).
                    Members warp in HIDDEN, then are revealed one every stagger_frames (6) --
                    warping first means NavMesh work never lands on the same frame as avatar
                    compositing.
     Arrival        The leader texts the player and a map marker drops. Each archetype has its
                    own arrival line.
     Order time     The leader texts the bulk contract. Businessmen 14:00, hippies 11:00, bikers
                    21:00, rock band 23:00. The offer is built with ContractInfoBuilder and handed
                    to NPCCustomer.OfferContract -- and then the SHIPPED pipeline runs: phone
                    accept, deal-window picker, CustomerAttendDealBehaviour, HandoverScreen,

                    real XP, real analytics receipt.

  ZERO HARMONY PATCHES IN THE CORE LOOP. The only patch in the whole mod is a prefix on
  NPCsLoader.Load that pre-registers the visitor prefabs by explicit type name just before the
  game reconstructs a save's NPCs. That is what makes the visitors appear in a save written BEFORE
  the mod was installed, and it avoids S1API's blanket assembly scan, which swallows
  Assembly.GetTypes() failures and would silently drop every visitor if any type in the DLL failed
  to load.

  THE MARGIN. The below-market rate is expressed as a smaller ContractInfo.Payment, never as a
  patched price formula. You experience it as "they pay less per unit but they will take
  everything". Quantities respect the shipped rounding rule (orders of 14+ snap to a multiple of
  five) and the shipped 1,000-unit hard clamp.

  THE INTERACTION FIX (2026-08-04, after playtest round 1)             [SHIPPED, UNVERIFIED]
  --------------------------------------------------------------------------------------------
  BUG 1 -- THE OFFER SILENTLY DID NOT SEND.  Customer.OfferContract(ContractInfo) returns VOID and
  walks away doing nothing if that customer already holds an unanswered OfferedContractInfo or a
  CurrentContract. The game's own string table carries the refusals: " already offered contract",
  " already has a contract", "Customer already has a pending offer". S1API's NPCCustomer wrapper
  around it returns TRUE whenever it does not throw, so the success value is meaningless -- and
  the mod was latching OfferSent = true on it.

  Worse, OfferedContractInfo survives save and load, so one unanswered offer wedges that customer
  permanently until something clears it.

  Now:
     - The leader is PRE-FLIGHTED before the call, and OfferedContractInfo is READ BACK
       afterwards. The flavour text only sends once that read confirms an offer is really there.
     - Stale offers and contracts are cleared across the whole eight-visitor pool on group
       ARRIVAL and on DEPARTURE, using the shipped Customer.ExpireOffer and Contract.Expire first
       and only nulling the field as a fallback.
     - A failed offer RETRIES up to three times per visit instead of latching.
     - "Clear the group's stuck order" is the manual escape hatch, and "Why can't I sell to them?"
       reports which of the six stages the sale is stalled at.

  BUG 2 -- TALKING TO A VISITOR OPENED AN EMPTY DIALOGUE.  Customer.SetUpDialogue is private and
  runs once in Customer.Start, which is BEFORE the mod writes CustomerData -- so the shipped
  sample / deal / complete-contract choices were built against zero spend and no direct approach,
  and a group member had a greeting and nothing else. The canvas opened on a node with no choices
  and Escape was the only way out.

  Now every member of a visiting group gets a real menu, APPENDED with AddDialogueChoice and never
  by overriding the container -- overriding hides the shipped "complete contract" choice, which is
  how a delivery is actually handed over.

     Leader        "About the <group> order" -> send it to my phone / status / something's stuck,
                   start over / later. Outcomes come back as an NPC line, because dialogue node
                   text is baked at build time and cannot be written at runtime.
     Non-leaders   "Talk business" -> "You buying?" hands off to the shipped street-deal flow
                   (handover, real money) plus "Who's running this?". With allow_walkup_sales =
                   false they keep the menu but only point at the leader.

  Either way the conversation exits cleanly. S1API's SetupDialog() is called to re-run the
  shipped dialogue build after customer data is written.

 8.  TUTORIAL QUEST LINE -- 6 chapters, 22 objectives in this package
==================================================================================================

  Real S1API quests, not a text file. 50 XP per chapter. Progress persists per save. Started from
  the TUTORIAL TAB on the Expansions screen, or from the main menu (where it arms itself and
  begins on load). Start / Restart and Reset are also still Core actions on the Actions tab.

  SIX CHAPTERS, 22 OBJECTIVES, ALL OF THEM REACHABLE. Nothing in the line self-completes and
  nothing is there to be explained away. On a machine that also has the separate mod named in the
  orientation note, one more chapter of two more objectives slots in between Diagnostics and
  Hireable Drivers -- seven chapters and 24 objectives there. Both numbers are given below
  wherever they differ; this package is the six-chapter case.

  HOW THE CHAPTERS ARE NUMBERED. They are not, in the code. Each chapter declares an integer
  Order and the registry sorts on it (ties broken by chapter id), so a chapter's number is purely
  its POSITION in that sorted list -- there is no "Chapter N" string anywhere in the suite. The
  Order values are 100 / 200 / 300 / 400 / 500 / 600 / 700, and 400 belongs to the chapter that
  does not register here, so the list simply closes up: Hireable Drivers, Police Improvements and
  Special Customers are positions 4, 5 and 6 in this package and positions 5, 6 and 7 on a machine
  with that mod. The only number the game ever shows you is the progress counter in the menu
  footer -- "Tutorial 3/6 - <objective>" -- and its denominator counts chapters you have left
  SWITCHED ON, so switching one off renumbers everything after it too. Do not treat the numbers
  below as identities; the Order value and the title are the stable things.

  Chapters 1-3 are Core's and were VERIFIED END-TO-END IN A LIVE GAME on 2026-08-03. So was the
  order-400 chapter, on the machine that has its mod, where it sits fourth. Chapters 4-6 here
  used to be placeholders reading "this chapter fills itself in as soon as the mod ships its
  objectives"; all three now have real objectives, and none of those have run.

  A chapter that cannot currently be attempted reports "coming soon" with the reason rather than
  blocking the line -- not installed, switched off, host-only and you are a guest, the module has
  not wired into a loaded game yet, or the mod the chapter is about is absent. The director turns
  such a chapter into ONE objective whose title is "<chapter title>: <reason>", and that objective
  completes itself about three seconds later so the line moves on.

  EVERY CHAPTER HAS AN ON/OFF SWITCH on the Tutorial tab, plus Enable all and Disable all. A
  switched-off chapter shows "Skipped", is stepped over by the director, and contributes no
  journal objectives. It is deliberately NOT marked complete, so switching it back on replays it.
  The set persists as one comma-separated list, tutorial_disabled_chapters, under [Expansions].

  ----------------------------------------------------------------------------------------------
  NEVER PUT A DOT IN A CONFIG CATEGORY NAME
  ----------------------------------------------------------------------------------------------
  MelonPreferences hands the identifier to its TOML writer unquoted, a dot is read as a table
  path, the module gets nested inside the parent table, and every entry it tries to write is
  SILENTLY DISCARDED. This was a real bug in this project: every module's "enabled" entry was
  never reaching disk, so disabling a module was lost on restart. Core now refuses to register a
  module whose category contains a dot.

  PREREQUISITES  (all already installed on this machine)
     1. MelonLoader 0.7.3 for Schedule I  -- provides MelonLoader\ and version.dll
     2. S1API (Forked) 3.1.7              -- Mods\S1API.Il2Cpp.MelonLoader.dll

        The S1APILoader plugin is still required; it selects the IL2CPP-vs-Mono flavour.
     3. The IL2CPP (default Steam) branch. Mono is not supported.

  WHERE EACH DLL GOES
  ----------------------------------------------------------------------------------------------
     <GameDir>\UserLibs\
         Expansions.Core.dll               shared library, NOT a MelonMod        v0.1.0

     <GameDir>\Mods\
         Expansions.HireableDrivers.dll    expansion mod                         v0.4.0
         Expansions.PoliceOverhaul.dll     expansion mod                         v0.2.0
         Expansions.SpecialCustomers.dll   expansion mod                         v1.0.0
         S1API.Il2Cpp.MelonLoader.dll      third-party API layer                 v3.1.7

     <GameDir>\Plugins\
         S1APILoader.MelonLoader.dll       third-party loader plugin             v3.1.7

  Expansions.Core.dll MUST be in UserLibs, not Mods. MelonLoader scans UserLibs before Plugins and
  Mods and registers it as a shared assembly search directory, so all three mods bind to a single
  copy. A copy sitting next to a mod in Mods\ would shadow it.

  The three expansion mods are independent. Install one, two, or all three -- Core handles any
  combination and produces exactly one per-frame fan-out regardless. Core alone still gives you
  the Expansions screen, the 16 Core actions, the 18-probe harness and three Core tutorial
  chapters -- six in total, because Core also registers a placeholder for each absent feature mod.

  Every project's <Version> matches the version its MelonInfo attribute declares:
  Expansions.HireableDrivers 0.4.0, Expansions.PoliceOverhaul 0.2.0,
  Expansions.SpecialCustomers 1.0.0. Expansions.Core is 0.1.0 and has no MelonInfo, because it is
  a library rather than a mod. An earlier revision documented a 0.3.0 / 0.4.0 disagreement on
  Hireable Drivers; there is no longer any mismatch anywhere in the suite.

  BUILDING FROM SOURCE
  ----------------------------------------------------------------------------------------------
         dotnet build src\Expansions.sln -c Release

     Auto-copies Expansions.Core.dll into <GameDir>\UserLibs and the three mod DLLs into
     <GameDir>\Mods on success.

     It builds with 0 errors and 0 warnings. The deploy target uses ContinueOnError, so a
     file-lock warning while the game is running is expected and harmless -- the copy is simply
     skipped. Pass -p:ExpansionsDeployDir= to skip the copy entirely and get a silent build.

     Target framework is net6.0. References resolve against
     <GameDir>\MelonLoader\Il2CppAssemblies and <GameDir>\MelonLoader\net6, plus the S1API.Forked
     3.1.7 NuGet package. Nothing is copied local: the S1API NuGet is explicitly excluded from the
     output because S1APILoader provides the runtime DLL.

     If you change the game path, edit the GameDir property in src\Directory.Build.props.

  REPOSITORY LAYOUT
  ----------------------------------------------------------------------------------------------
     src\Expansions.sln       the expansion suite: Core plus three mods -- everything this
                              document describes
     research\                IL2CPP API reference docs, the three implementation plans, and the
                              raw metadata dumps that back them
     research-ext\            external research: design intent, mod-ecosystem survey, UI style
     tools\                   asset-extraction tooling (AssetStudio, AssetRipper). Not shipped.
     CONTEXT.md               the project's shared working memory -- decisions, gotchas, state

     The repo root also holds a second, separate mod that is NOT part of this package and is not
     described here -- see the orientation note at the top of this file. It has its own project
     file and its own build command; nothing in src\ references it and nothing in it references
     src\.

     A root Directory.Build.props excludes src\, research\, research-ext\ and _backup\ from that
     root project's source glob. Do not remove it: the root project globs **/*.cs from the repo
     root, and a stray Cpp2IL dummy Assembly-CSharp.dll in a backup folder will silently hijack
     the real reference and break every game-type import.

 12.  WHAT TO TEST FIRST -- the ten checks that matter
==================================================================================================

  Playtest round 1 established that the suite loads, the native screen opens and the probes run.
  It also found six real bugs. Everything below round 1 is either a fix that has never executed
  or a feature that has never executed. These ten are ordered so that an early failure saves you
  the later ones, and the first three are the round-1 fixes -- if those are still broken, nothing
  after them is worth your time.

  Do them on a save you are willing to lose. SaveGame_3 has already been mutated by testing, and
  there is a full pre-test backup of the entire Saves folder at _backup\saves-20260803-214245\.

   1. Load a save, press F7, and SCROLL THE ACTION LIST WITH THE MOUSE WHEEL.
      This is check number one because in round 1 the wheel did nothing anywhere on the screen and
      only about five of the actions could be reached at all.
      PASS: the list scrolls, a thin scrollbar appears in the right-hand gutter, and PgUp / PgDn /
      Home / End / arrows work too. Then confirm the three counts: an ACTIONS / TUTORIAL / MODS
      tab strip, 47 action rows in FOUR groups -- and one of those groups must be headed "Police
      Improvements" with eight rows starting "Police:".
      FAIL, no scrolling: the transparent raycast catcher on the ScrollRect viewport is not doing
      its job. FAIL, no Police heading: the log will say "Registered 0/8"; the typed-call fix did
      not take.

   2. On the same screen, collapse the output pane with its Hide control, then press Escape,
      reopen with F7, and check it is still collapsed. Then open any picker and TYPE INTO IT.
      PASS: the collapsed state survived (output_pane_open persisted), and typing filters the list
      WITHOUT walking your character around the world.
      FAIL on the typing: the screen could not take StateProperties.UIDefault. The log carries the
      reason once, and the workaround is to scroll rather than type.

   3. Run "Run all diagnostics probes" from the Actions tab.
      PASS: 41 results and a report path in the output pane.
      FAIL: the plain IMGUI "Schedule I Expansions" window instead of the native screen (the
      injector never landed), or far fewer than 41 results (a module did not enable).
      While you are in the report, read drivers.vehicle_agent. At least one owned vehicle listed
      as "self-drives: yes" means you get the real driving path; all "no" is not a bug, but every
      trip will relay, so ignore anything in section 5 about roads and judge the feature purely on
      whether goods arrive.

   4. THE NEW HIRING FLOW. Walk up to the employee fixer you normally buy botanists from.
      PASS: their conversation carries one extra line per owned property with a free driver slot,
      reading like "Hire a driver for the Barn ($1,800)". Pick one; you are charged and a driver
      appears.
      FAIL: no such line. Read drivers.hiring_desk -- it distinguishes "no
      DialogueController_Fixer in the scene" from "the NPC exists but would not take a choice".
      Either way the Expansions menu's "Hire a driver (fallback)" action ungreys itself, so you
      can still get a driver and continue with check 5.

   5. THE CLIPBOARD. Point the management clipboard at that driver.
      PASS: you get Bed, Stations and five Route rows. Stations refuses with "Drivers run transit
      routes, not stations." Set the Bed. Then set a route's pickup with the worldspace picker --
      hovering a container at a DIFFERENT property must refuse with "Driver X only collects from
      the Barn", and a container at the hiring property must accept. Set a drop-off at another
      property you own; the vanilla out-of-range refusal must be overturned.
      FAIL: the rows are absent or the constraint does not show. drivers.clipboard reports whether
      the RouteEntryUI.ObjectValid patch landed.
      Then "Start a run now" and watch. PASS: the driver leaves and the destination stock goes up.
      FAIL: it stays Idle -- press F6 and read the no-work reason, which is the diagnosis.

   6. Start a trip and then sleep through it.
      PASS: you wake to "Delivery completed while you slept" and the cargo is at the far end.
      FAIL: a van parked mid-junction, a driver stuck in a non-Idle state, or cargo that vanished
      -- the time-skip collapse is the least testable path in the mod and the most likely to be
      wrong.

   7. THE UNWEDGED SALE LOOP. "Bring a group into town now", then "Make the group offer now",
      accept on the phone, and complete the handover.
      PASS: an offer message arrives WITH RESPONSE BUTTONS, you accept, the leader walks to the
      meeting point, and the shipped handover screen pays you with real XP and an analytics
      receipt.
      FAIL at the offer: run "Why can't I sell to them?" and read which of the six stages it stops
      at. A stop at stage 2 with a "leader already holds an offer" note is the round-1 bug not
      fixed; use "Clear the group's stuck order" and try again. A stop at stage 4 means the
      message reached the phone with no response buttons, which cannot be accepted.
      Also WALK UP TO A GROUP MEMBER AND TALK TO THEM. In round 1 that opened an empty dialogue
      with no way out but Escape. The leader must offer "About the <group> order" and non-leaders
      "Talk business", and the shipped "complete contract" choice must still be in the list.

   8. Use "Police: heat +25" twice, then walk past a patrol.
      PASS: police.world_state reports a driven intensity above the vanilla baseline and a 2-3
      officer band, and you can see more officers per post. FAIL: intensity unchanged -- the
      OnUncappedMinPass postfix did not land, and police.patches names which target missed.
      Then get arrested while carrying less cash than the fine. PASS: the notice shows the
      multiplied figure, cash goes to zero, and the shortfall comes off your ONLINE balance with a
      notification. FAIL: charged twice (the self-calibration read the wrong boundary), or not at
      all.

   9. Use "Police: spawn federal agent".
      PASS: agents appear and the log names the strategy (registered prefab, or cloned officer).
      FAIL: "Federal agents unavailable" -- record the reason; that pillar is simply off on this
      build and nothing else is affected. Then SAVE, RELOAD, and confirm the NPC set is unchanged:
      an agent that reached the save is the one genuinely dangerous outcome here.

  10. Save, quit to the main menu, reload the same save, and re-run the whole probe suite.
      PASS: heat records, the driver roster and trip counters, the clipboard's route rows and the
      group state all come back identical, and identity.player_code matches the earlier report.
      FAIL: anything reset -- and note that driver ROUTES now live in the vanilla save, not the
      mod's blob, so this is the first check that the vanilla round trip actually works. A
      PlayerCode that changed means heat is keyed to the wrong thing.

  One thing NOT on this list on purpose: do not enable allow_mutating_probes. The read-only

  DISABLE, DO NOT DELETE                                                    *** IMPORTANT ***
  --------------------------------------------------------------------------------------------
  A save-persisted custom NPC cannot be unmade by a toggle. S1API builds the eight Special

  read. Disabling the module stops everything the mod DOES -- no visits, no offers, no dressing --
  but the NPCs stay in the world and in the save. Destroying a save-persisted networked NPC
  mid-session risks corrupting the save, so the module deliberately does not try.

  Removing the DLL is what removes them, and that ORPHANS THEIR FOLDERS in every save that stored
  them. Whether the vanilla NPC loader tolerates orphaned folders is an open question with a
  written test recipe (SC-V6) in the probe report, and it is release-blocking.

  Use the toggle on the Mods tab, or set enabled = false in Expansions.cfg. Do not delete the DLL
  from Mods\.

  The other two mods do not have this problem. Drivers are real vanilla employees created by the
  game's own factory: disabling reverts them to ordinary Handlers with no stations and no routes,
  and the save still loads. Federal agents have ShouldSave forced false and are removed from both
  registries on despawn, so they cannot reach the save at all.

  --------------------------------------------------------------------------------------------
  MULTIPLAYER AND HOST AUTHORITY
  --------------------------------------------------------------------------------------------
  - The expansion mods are HOST-AUTHORITATIVE. All world mutation is gated on
    InstanceFinder.NetworkManager == null || InstanceFinder.IsServer. The null check is
    load-bearing: single-player has no NetworkManager at all, so a bare IsServer check would
    disable the mods outside multiplayer.
  - A co-op guest gets a read-only surface. Host-only actions grey themselves out naming the
    reason ("host only - this peer is a client") rather than silently doing nothing. A guest can
    still teleport to things and read status -- moving your own camera is client-side.
  - A guest tracks a Special Customers visit so the menu, tutorial and status read correctly, but
    never re-warps or re-reveals anybody. The host owns the world and the guest receives the group
    already placed.
  - ALL PLAYERS SHOULD INSTALL THE SAME MODS. There are no custom network messages: the game runs
    FishNet v3, and FishNet's code generator never runs against mod assemblies on IL2CPP, so
    custom RPCs, SyncVars and spawnable prefab ids are simply unavailable.
  - Custom NPC prefabs are registered by simple type name and the ordering is load-order
    sensitive, so co-op peers must agree on emission order. sc.visitor_prefab dumps that ordering
    -- diff it between two machines before trusting co-op.

  --------------------------------------------------------------------------------------------
  TYPING IN A MENU PICKER USED TO MOVE YOUR CHARACTER               *** FIXED, UNVERIFIED ***
  --------------------------------------------------------------------------------------------
  Observed in round 1. The picker's search box reads Input.inputString, and the screen lives on a
  standalone canvas that was not part of the game's MonoState / StateProperties stack, so
  keystrokes reached gameplay as well. Typing "marcus" into the NPC teleport search walked you
  around the world while you typed it.

  The screen now reads StateProperties.UIDefault and calls
  StatePropertiesTransitionHandler.Transition on open, saving and restoring whatever the game was
  previously enforcing -- the game's own preset for its own UI, which locks movement and camera
  look and frees the cursor. The per-frame Cursor.lockState write is kept only as a fallback.

  If the transition cannot be taken, the log says why ONCE and the old behaviour returns. The
  workaround is unchanged: scroll rather than type, or use the direct rows that need no search.
  The F6 drivers panel is not part of the state stack at all -- it is read-only, so it has no
  pickers to type into.

  THE SPECIAL CUSTOMERS SCOUT HAS BEEN SEEN OFF-POST            *** OUTSTANDING, UNDIAGNOSED ***
  --------------------------------------------------------------------------------------------
  Marcus Vale is configured for the Northtown motel forecourt, and a 2026-08-03 probe found him
  there with about 1 m of drift. During round 1 the owner found him at roughly (-82.3, -3.9, 66.7)
  -- in WESTVILLE, and about four metres below the expected ground plane. He appears to wander

  Not investigated. Nothing has been changed to address it. "Send the scout back to his post"

  will not stay parked also affects where a group assembles.

  --------------------------------------------------------------------------------------------
  FEDERAL AGENTS MAY NOT BE SPAWNABLE ON THIS BUILD AT ALL
  --------------------------------------------------------------------------------------------
  Both spawn strategies are conditional. "PoliceNPC" may not be a registered FishNet spawnable,
  and the clone path needs a live officer to exist. If neither works, Spawn returns 0, the reason
  is logged, and the other four pillars are unaffected -- but the whole federal-agent feature and
  the last objective of the police tutorial chapter simply do not happen.

  A CLONED AGENT INHERITS THE DONOR OFFICER'S NPC ID. The id lives on a shared asset, and
  rewriting it would rename every officer in the game. So on the clone path you will have two NPCs
  answering to the same id. They are distinguished by native pointer, never added to the officer
  pool, and cannot reach the save -- but anything that looks an officer up by id can find the
  wrong one.

  --------------------------------------------------------------------------------------------
  WRITING AN IL2CPP CONST KILLS THE PROCESS
  --------------------------------------------------------------------------------------------
  Codebase-wide danger, and the reason allow_mutating_probes exists and defaults off.
  Il2CppInterop projects a const and a real static as the same read/write property. The setter is
  a bare il2cpp_field_static_set_value which, unlike Mono's, has NO literal guard: it computes
  klass->static_fields + offset and memcpys. A const contributes no storage, so on a class whose
  statics are all const that base pointer is null -- access violation, process gone, nothing
  catchable, no crash log. Reads are fine.

  28 of the 31 police tuning statics are consts. GameReflection.TryWriteStatic now refuses
  const-inlined statics, and the crash journal quarantines any subject the process died on. Do
  not add a static write anywhere without checking il2cpp_field_get_flags for LITERAL first.

  --------------------------------------------------------------------------------------------
  SPECIAL CUSTOMERS AND THE OFFICIAL FEATURE
  --------------------------------------------------------------------------------------------
  TVGS is shipping their own Special Customers as v0.5.0, expected within weeks. The detector
  described in section 7 is now BUILT and fails closed, so updating past 0.4.6 should stand the
  module down on its own. That has never been tested against a real 0.5.0 build, and the resolved
  game version string is itself unconfirmed -- "0.4.6f11" has only ever been observed inside save
  JSON. If the version cannot be parsed the module disables, which is the safe direction.

  --------------------------------------------------------------------------------------------
  MODULE ERROR HANDLING
  --------------------------------------------------------------------------------------------
  A module that throws 10 times in one frame hook during a single enable cycle is switched off for
  the rest of the session. The PERSISTED toggle stays on, so it retries on next launch. If a
  module keeps disappearing from the active set, check the MelonLoader log for the ten error lines
  that preceded it.

  --------------------------------------------------------------------------------------------
  FIRST LAUNCH AFTER THE TOOLCHAIN UPGRADE NEEDS INTERNET
  --------------------------------------------------------------------------------------------
  MelonLoader 0.7.3 regenerates the Il2CppAssemblies and downloads Cpp2IL .21 on first launch.
  That launch will not complete offline. Subsequent launches are fine. A backup of the pre-upgrade
  install exists at _backup\2026-08-03_191117\ (gitignored); rolling back also means restoring
  S1API.Forked to 3.1.4 in src\Directory.Build.props, and in the root project file if you build
